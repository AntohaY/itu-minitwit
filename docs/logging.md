## Project Facts

### What We Implemented

- The Go application uses `log/slog` with a JSON handler writing to stdout.
- `LOG_LEVEL` can set log level to debug, warn, or error; the default is info.
- `BeforeAfterMiddleware` logs request start/end events and attaches a request ID.
- API and UI handlers log validation failures, database failures, successful operations, and selected debug events.
- Request IDs can come from `X-Request-ID` or be generated by the middleware.
- The app also has an application error tracker that writes to `/app/logs/errors_history.log` and `/app/logs/errors_tracker.log`.
- Sensitive-message sanitization exists in `src/helpers/logsanitize/logsanitize.go` for the custom error tracker.
- The production stack uses Promtail and Loki.
- `monitoring/promtail/config.yml` scrapes Docker JSON container logs from `/var/lib/docker/containers/*/*-json.log`.
- Promtail pushes logs to `http://loki:3100/loki/api/v1/push`.
- Grafana is provisioned with Loki as a data source.
- PR #113 added the earlier rsyslog-to-Promtail/Loki path: https://github.com/AntohaY/itu-minitwit/pull/113.
- Later deployment changes removed `central-rsyslog` from the remote stack and use Promtail directly against Docker JSON logs, so the final report should describe the current remote stack rather than the older rsyslog design unless the team confirms rsyslog is still deployed.

### Known Gaps / Needs Team Evidence

- `query-logs.sh` expects a `central-rsyslog` service, but the remote production stack in `remote_files/docker-stack.yml` uses Promtail directly against Docker logs and does not define `central-rsyslog`. The team should clarify which logging path is actually used in production.
- The root `docker-stack.yml` and historical PR #113 contain a central rsyslog setup, but the remote production stack differs.
- Promtail config extracts Docker log fields and container IDs, but it does not add rich labels such as service, stack, environment, or request ID.
- Need current logging dashboard URL and screenshots for the final report.
- Need retention settings for production Loki; the repository uses Loki's local config default unless changed elsewhere.

### Oral Exam Answer

The application emits structured JSON logs with request IDs, and production logging is intended to centralize Docker container logs through Promtail, Loki, and Grafana. Logs are useful for investigating API failures, deployments, and user-flow errors. A key thing to be honest about is that the repo contains two logging approaches, rsyslog and Promtail-to-Loki, so the team must explain which one is actually deployed.
